1 Introduction and Learning Objectives

1.1 The Power of Tree-Based Models in Healthcare

In healthcare analytics, we often face prediction problems where the relationships between patient characteristics and outcomes are complex and non-linear. Consider these real-world scenarios that healthcare managers encounter daily:

  • Predicting healthcare costs: A patient’s annual healthcare expenditure depends on age, chronic conditions, prior utilization, and many other factors. These relationships are rarely simple linear associations—a 70-year-old diabetic patient with heart disease doesn’t simply cost “the sum” of these individual risk factors.

  • Estimating length of stay: Hospital administrators need accurate predictions for bed management and staffing. A patient’s expected length of stay depends on diagnosis, comorbidities, surgical procedures, and complications, often in complex, interacting ways.

  • Forecasting resource utilization: Health systems must anticipate demand for services. Utilization patterns vary dramatically across patient subgroups defined by combinations of clinical and demographic characteristics.

Traditional linear regression assumes that each predictor contributes additively to the outcome, with a constant effect across all patients. But in healthcare, this assumption often fails dramatically. For example, the effect of diabetes on healthcare costs might be minimal for young, otherwise healthy patients but substantial for elderly patients with multiple comorbidities. Tree-based models excel at capturing these kinds of complex interactions automatically, without requiring the analyst to specify them in advance.

1.2 Why Trees? The Intuition Behind Recursive Partitioning

The fundamental idea behind tree-based prediction is elegantly simple: divide patients into groups with similar outcomes, then predict the average outcome for each group. This process of recursive partitioning creates a hierarchical structure that resembles an inverted tree, with the root at the top containing all patients and branches leading down to “leaves” (terminal nodes) containing homogeneous subgroups.

Consider predicting annual healthcare costs. A tree algorithm might first split patients into those with prior-year costs above versus below $10,000. Among high-cost patients, it might further split by age (over 65 vs. under 65). Among low-cost patients, it might split by presence of chronic conditions. This continues until we have groups that are relatively homogeneous in their healthcare costs.

The beauty of this approach is that:

  1. Interactions are automatic: If diabetes only matters for elderly patients, the tree will naturally split by age first, then by diabetes only in the elderly branch.

  2. Non-linearities are handled: The tree doesn’t assume that the effect of age is linear—it can create different predictions for ages 20-40, 40-60, and 60-80 if that’s what the data support.

  3. Results are interpretable: A tree can be visualized and explained to non-technical stakeholders. “Patients over 65 with prior hospitalization and diabetes are predicted to cost $45,000” is much more accessible than a regression equation.

  4. No variable scaling needed: Unlike penalized regression, trees are invariant to monotonic transformations of predictors—you don’t need to worry about standardization.

1.3 Connection to Last Week: The Prediction Framework

Last week, we learned about penalized regression methods (Ridge, LASSO, Elastic Net) for prediction. This week, we explore an entirely different approach to the same fundamental problem: predicting outcomes from patient characteristics while avoiding overfitting.

Both approaches share common principles:

  • Training vs. test data: We evaluate predictive performance on data not used to build the model
  • Cross-validation: We use CV to select tuning parameters that balance bias and variance
  • Regularization: We control model complexity to prevent overfitting

However, the methods differ fundamentally in how they model the relationship between predictors and outcome:

2 Conceptual Foundations

2.1 How Trees Make Predictions: The Big Picture

Before diving into the algorithmic details, let’s understand the conceptual framework. A regression tree predicts a continuous outcome (like healthcare costs) by:

  1. Partitioning the predictor space into rectangular regions
  2. Assigning a predicted value to each region (the average outcome of training observations in that region)

For a new patient, we simply determine which region their predictor values fall into and predict the corresponding average. This is fundamentally different from regression, which computes a weighted sum of predictor values.

2.1.1 Visual Intuition

Imagine predicting healthcare costs based on just two variables: age and number of chronic conditions. A regression tree might create predictions like this:

  • Region 1: Age < 50 AND Conditions < 2 → Predict $3,000
  • Region 2: Age < 50 AND Conditions ≥ 2 → Predict $8,500
  • Region 3: Age ≥ 50 AND Conditions < 3 → Predict $12,000
  • Region 4: Age ≥ 50 AND Conditions ≥ 3 → Predict $35,000

Notice how the tree captures an interaction: for younger patients, having 2+ conditions increases predicted costs from $3,000 to $8,500 (a 2.8x increase). For older patients, going from <3 to ≥3 conditions increases predicted costs from $12,000 to $35,000 (a 2.9x increase). The tree automatically discovered that the “cost impact” of chronic conditions varies by age group.

2.2 The Recursive Partitioning Algorithm

Now let’s understand how the algorithm constructs these partitions. The process is called “recursive binary splitting” because at each step, we:

  1. Consider all possible ways to split the current region into two parts
  2. Choose the split that most improves our predictions
  3. Recursively apply the same process to each resulting region

2.2.1 Step 1: Finding the Best Split

At each node, we need to decide: - Which variable to split on - What value to use as the cutoff

For a regression tree predicting a continuous outcome Y, the algorithm evaluates every possible split by computing the reduction in sum of squared errors (SSE).

Suppose we’re considering splitting predictor X at value c, creating two groups:

  • Left group (R₁): Observations where X < c
  • Right group (R₂): Observations where X ≥ c

For each group, the predicted value is simply the mean of Y for observations in that group:

\[\hat{y}_{R_1} = \frac{1}{n_1} \sum_{i: x_i < c} y_i \quad \text{and} \quad \hat{y}_{R_2} = \frac{1}{n_2} \sum_{i: x_i \geq c} y_i\]

The SSE for this split is:

\[\text{SSE}(X, c) = \sum_{i: x_i < c} (y_i - \hat{y}_{R_1})^2 + \sum_{i: x_i \geq c} (y_i - \hat{y}_{R_2})^2\]

The algorithm tries every variable and every possible cutoff value, selecting the combination (X, c) that minimizes SSE. This is a “greedy” approach—we make the locally optimal choice at each step without considering whether a different choice might lead to a better tree overall.

2.2.2 Step 2: Recursive Splitting

Once we’ve made the first split, we have two regions. We now apply the exact same process to each region independently:

  1. Among observations in the left region, find the best split
  2. Among observations in the right region, find the best split
  3. Continue recursively on each resulting region

This process creates a tree structure where each internal node represents a split decision and each terminal node (leaf) represents a prediction.

2.2.3 Step 3: Stopping Criteria

The algorithm must know when to stop splitting. Common stopping criteria include:

  • Minimum node size: Don’t split nodes with fewer than some threshold of observations (e.g., 20)
  • Maximum depth: Limit the number of levels in the tree
  • Minimum improvement: Stop if no split improves SSE by more than a threshold

However, these early stopping rules are often too aggressive—they might prevent a “good” split that would occur later. Instead, modern implementations typically grow a large tree and then prune it back.

2.3 Overfitting and the Need for Pruning

2.3.1 The Problem: Trees Can Perfectly Fit Training Data

If we let a tree grow without restriction, it will continue splitting until each terminal node contains very few observations (perhaps even just one). Such a tree will have:

  • Zero training error: Each prediction equals the actual outcome
  • Poor test performance: The tree has memorized the training data, including its random noise

This is overfitting in its purest form. The tree is too complex—it has high variance (predictions change dramatically with different training samples) even though it has low bias (it can approximate any pattern).

2.3.2 Visual Illustration of Overfitting

Consider predicting healthcare costs from age alone. Imagine we have 100 patients:

  • A 1-split tree might divide patients into age < 50 vs. ≥ 50, giving 2 predictions
  • A 10-split tree creates 11 predictions, each based on roughly 9 patients
  • A 99-split tree creates 100 predictions, each based on 1 patient

The 99-split tree fits the training data perfectly but will perform terribly on new data because each prediction is based on a single patient’s random cost variation.

2.3.3 The Solution: Cost-Complexity Pruning

Rather than deciding when to stop growing, we grow a large tree and then prune branches that don’t improve test performance enough to justify their complexity. This is done by minimizing a penalized error criterion:

\[\text{Cost-Complexity} = \text{SSE} + \alpha \cdot |T|\]

Where: - SSE is the sum of squared errors on the training data - |T| is the number of terminal nodes in the tree - α (alpha) is a complexity parameter that controls the tradeoff

This should look familiar from last week! Just as LASSO penalizes regression coefficients to achieve a simpler model, cost-complexity pruning penalizes tree size. The parameter α plays the same role as λ in penalized regression:

  • α = 0: No penalty → full tree (overfitting)
  • α large: Heavy penalty → small tree (underfitting)

We use cross-validation to find the optimal α that minimizes prediction error.

2.3.4 The 1-SE Rule

When selecting α via cross-validation, we often use the “one standard error rule”:

  1. Compute the cross-validated error for each value of α
  2. Find α* that minimizes CV error
  3. Select the largest α (simplest tree) whose CV error is within one standard error of the minimum

This rule trades a tiny bit of predictive accuracy for a substantially simpler, more interpretable tree. In practice, the simpler tree often performs just as well on truly new data.

2.4 Advantages and Limitations of Trees

2.4.1 Advantages

  1. Interpretability: Trees can be visualized and explained to non-technical stakeholders. You can literally trace the path from root to leaf and understand why a prediction was made.

  2. No preprocessing required: Trees handle numeric and categorical predictors naturally, don’t require scaling/standardization, and are invariant to monotonic transformations.

  3. Automatic interaction detection: If diabetes only matters for elderly patients, the tree will discover this automatically.

  4. Handle missing data: Trees can use “surrogate splits” to make predictions when some values are missing.

  5. Computationally efficient: Predictions are extremely fast—just a series of if-then comparisons.

2.4.2 Limitations

  1. High variance: Small changes in the training data can lead to very different trees. This instability is the primary motivation for ensemble methods.

  2. Piecewise constant predictions: Trees approximate smooth relationships with step functions, which can be inefficient when the true relationship is smooth.

  3. Greedy algorithm: The recursive splitting may miss globally optimal solutions because it doesn’t look ahead.

  4. Extrapolation issues: Trees cannot extrapolate beyond the range of training data—they simply predict the average of the nearest terminal node.

  5. Not ideal for additive relationships: If the true model is Y = β₁X₁ + β₂X₂ (purely additive), a tree needs many splits to approximate this, while linear regression captures it exactly.

3.2 Creating a Healthcare Cost Prediction Dataset

For this tutorial, we’ll create a realistic simulated dataset representing patients in a healthcare system. Our goal is to predict annual healthcare costs based on patient characteristics, health conditions, and prior utilization. This mirrors the Medical Expenditure Panel Survey (MEPS) data that you’ll use for the assignment.

3.2.1 The Data Generation Process

We’ll simulate data that captures several realistic features of healthcare cost prediction:

  1. Non-linear age effects: Healthcare costs don’t increase linearly with age—they rise more steeply after 60
  2. Interactions: The effect of chronic conditions depends on age
  3. Heavy-tailed costs: Healthcare spending has many low-cost patients and some very high-cost outliers
  4. Multiple predictor types: Both continuous (age, BMI) and categorical (insurance, region) variables

Let’s create this dataset:

Show code 
# Create simulated healthcare cost dataset
n <- 1000  # Number of patients

# Generate patient characteristics
healthcare_data <- data.frame(
  # Demographics
  age = round(runif(n, 18, 85)),
  sex = sample(c("Male", "Female"), n, replace = TRUE),

  # Health behaviors and conditions
  bmi = round(rnorm(n, 28, 6), 1),
  smoker = sample(c(0, 1), n, replace = TRUE, prob = c(0.8, 0.2)),

  # Chronic conditions (more likely with age)
  diabetes = NA,
  hypertension = NA,
  heart_disease = NA,

  # Healthcare access
  insurance = sample(c("Private", "Medicare", "Medicaid", "Uninsured"),
                     n, replace = TRUE, prob = c(0.5, 0.25, 0.15, 0.1)),

  # Prior utilization
  prior_er_visits = rpois(n, lambda = 0.5),
  prior_hospitalizations = rpois(n, lambda = 0.15),

  # Geography
  region = sample(c("Northeast", "Midwest", "South", "West"),
                  n, replace = TRUE)
)

# Generate chronic conditions with age-dependent probabilities
# This creates realistic correlations between age and chronic conditions
healthcare_data <- healthcare_data %>%
  mutate(
    # Diabetes more likely with age and high BMI
    diabetes = rbinom(n, 1, plogis(-3 + 0.03 * age + 0.05 * bmi)),

    # Hypertension more likely with age
    hypertension = rbinom(n, 1, plogis(-2 + 0.04 * age)),

    # Heart disease more likely with age, smoking, and other conditions
    heart_disease = rbinom(n, 1, plogis(-4 + 0.05 * age + 0.5 * smoker +
                                         0.3 * diabetes + 0.3 * hypertension)),

    # Count of chronic conditions
    n_conditions = diabetes + hypertension + heart_disease
  )

# Generate healthcare costs with realistic complexity
# This is the "true" relationship that our models will try to discover
healthcare_data <- healthcare_data %>%
  mutate(
    # Base cost depends on age (non-linear)
    base_cost = 1000 + 50 * age + 0.5 * age^2,

    # Condition costs (with interactions!)
    condition_cost = 3000 * diabetes + 2500 * hypertension +
                     5000 * heart_disease +
                     # Interaction: conditions cost more for older patients
                     50 * age * n_conditions,

    # Utilization-driven costs
    utilization_cost = 2000 * prior_er_visits +
                       15000 * prior_hospitalizations,

    # Behavior costs
    behavior_cost = 1500 * smoker + 50 * pmax(bmi - 30, 0),

    # Insurance effects (uninsured have lower recorded costs due to less care)
    insurance_effect = case_when(
      insurance == "Private" ~ 1.0,
      insurance == "Medicare" ~ 1.1,  # Higher utilization
      insurance == "Medicaid" ~ 0.9,
      insurance == "Uninsured" ~ 0.6
    ),

    # Combine all components
    expected_cost = (base_cost + condition_cost + utilization_cost +
                     behavior_cost) * insurance_effect,

    # Add realistic noise (log-normal to create heavy tail)
    annual_cost = round(expected_cost * exp(rnorm(n, 0, 0.3)))
  ) %>%
  # Clean up intermediate variables
  select(-base_cost, -condition_cost, -utilization_cost,
         -behavior_cost, -insurance_effect, -expected_cost)

# Convert categorical variables to factors
healthcare_data <- healthcare_data %>%
  mutate(
    sex = factor(sex),
    insurance = factor(insurance),
    region = factor(region),
    smoker = factor(smoker, labels = c("No", "Yes")),
    diabetes = factor(diabetes, labels = c("No", "Yes")),
    hypertension = factor(hypertension, labels = c("No", "Yes")),
    heart_disease = factor(heart_disease, labels = c("No", "Yes"))
  )

3.4.2 The Complexity Parameter (cp)

The complexity parameter cp is the most important tuning parameter. It controls the cost-complexity pruning discussed earlier:

  • A split is only performed if it improves the model by at least cp * (SSE of root node)
  • Higher cp → fewer splits → simpler trees
  • Lower cp → more splits → complex trees

4 Extension to Random Forests

4.1 The Problem with Single Trees

While regression trees are interpretable and capture complex relationships, they suffer from a critical problem: high variance. This means that small changes in the training data can lead to very different trees, making predictions unstable.

4.2 The Random Forest Solution

Random forests address tree instability through two key ideas:

4.2.1 1. Bagging (Bootstrap Aggregating)

Instead of building one tree, we build many trees on different bootstrap samples and average their predictions:

  1. Draw B bootstrap samples from the training data
  2. Fit a tree to each sample
  3. For prediction, average across all B trees

This reduces variance because the averaging smooths out the individual trees’ errors. If each tree has variance σ², and the trees are independent, the ensemble has variance σ²/B.

4.2.2 2. Random Feature Selection

Bagging alone isn’t enough—the trees are too correlated because they all use the same best predictors at the top. Random forests add another layer of randomness:

  • At each split, only consider a random subset of m predictors (not all p)
  • This decorrelates the trees, making the averaging more effective
  • Default: m = p/3 for regression, m = √p for classification

5.1.1 Question 1: Algorithm Understanding

A regression tree is being built to predict hospital length of stay. The algorithm is considering splitting patients by age at cutoff 65. There are 200 patients younger than 65 with mean LOS = 3.2 days, and 100 patients 65+ with mean LOS = 5.8 days.

  1. What would be the prediction for a 70-year-old patient after this split?
  2. If the overall mean LOS before the split is 4.07 days, calculate the reduction in SSE from this split.
  3. Why is finding the optimal split computationally intensive with continuous predictors?
TipClick for Answers

  1. 5.8 days - The prediction for any patient in a terminal node is the mean outcome of training observations in that node. A 70-year-old falls in the 65+ node with mean LOS = 5.8.

  2. Reduction in SSE:

Before split: SSE = Σ(yᵢ - 4.07)² for all 300 patients

After split: SSE = Σ(yᵢ - 3.2)² for 200 young + Σ(yᵢ - 5.8)² for 100 old

The reduction = SSE_before - SSE_after

While we can’t compute exact values without individual data, the intuition is that predictions are now closer to actual values because we’ve separated two groups with different means.

  1. For a continuous predictor with n unique values, there are (n-1) possible cutoff points to evaluate. For each cutoff, we must compute the SSE for both resulting groups. With many predictors and many observations, this requires checking thousands of potential splits at each node.

5.1.2 Question 2: Overfitting and Pruning

Explain why a regression tree with 100 terminal nodes fit to 100 training observations would be useless for prediction, even though its training MSE is zero.

TipClick for Answer

This tree has perfectly memorized the training data—each terminal node contains exactly one observation, so the prediction equals the actual value and training MSE is zero.

However, the predictions reflect individual patient variation, not true underlying patterns. When applied to new patients, the tree will:

  1. Assign them to a terminal node based on the path they follow
  2. Predict the single training observation’s outcome in that node
  3. This prediction is essentially random from the new patient’s perspective

This is extreme overfitting. The model has high variance (predictions would change completely with different training data) and will perform poorly on test data. Pruning reduces the tree to capture genuine patterns rather than noise.

5.1.3 Question 3: Method Comparison

For each scenario, explain which method (linear regression, LASSO, regression tree, or random forest) would be most appropriate:

  1. Predicting healthcare costs for a health plan with 500 members using 10 predictors. Interpretability is essential for explaining to executives.

  2. Building a real-time risk scoring system for an EHR that must predict patient deterioration using 200+ clinical variables.

  3. Analyzing the relationship between hospital characteristics and readmission rates for a policy study.

TipClick for Answers

  1. Regression Tree - With only 500 observations and the need for interpretability, a pruned regression tree provides an easy-to-explain model. Random forest would give better predictions but can’t be visualized. LASSO could work but produces coefficient-based explanations that may be harder for executives.

  2. Random Forest - With 200+ variables and real-time prediction needs, random forest handles many predictors well, automatically selects important variables, doesn’t need preprocessing, and predictions are fast once trained. The lack of interpretability matters less in automated systems.

5.1.4 Question 4: Random Forest Mechanics

In a random forest with 500 trees predicting healthcare costs from 12 variables:

  1. How many variables would typically be considered at each split?
  2. Why does considering only a subset of variables at each split improve the ensemble?
  3. What is out-of-bag (OOB) error and why is it useful?
TipClick for Answers

  1. m = 12/3 = 4 variables per split (default for regression is p/3).

  2. Decorrelates the trees: If all trees considered all variables, they would all split on the same strongest predictor at the root, making them very similar. By randomly restricting the variables considered, different trees emphasize different predictors, making the ensemble more diverse. When we average diverse predictions, errors cancel out better than when averaging similar predictions.

  3. OOB error: Each bootstrap sample includes only about 63% of observations. The remaining 37% are “out-of-bag” for that tree. We can predict these using the tree and compare to actual values. Averaging across all trees gives an error estimate without needing a separate test set. It’s useful because:

    • No need to set aside test data
    • More efficient use of training data
    • Unbiased estimate of test error

# Introduction and Learning Objectives

## The Power of Tree-Based Models in Healthcare

In healthcare analytics, we often face prediction problems where the relationships between patient characteristics and outcomes are complex and non-linear. Consider these real-world scenarios that healthcare managers encounter daily:

- **Predicting healthcare costs**: A patient's annual healthcare expenditure depends on age, chronic conditions, prior utilization, and many other factors. These relationships are rarely simple linear associations—a 70-year-old diabetic patient with heart disease doesn't simply cost "the sum" of these individual risk factors.

- **Estimating length of stay**: Hospital administrators need accurate predictions for bed management and staffing. A patient's expected length of stay depends on diagnosis, comorbidities, surgical procedures, and complications, often in complex, interacting ways.

- **Forecasting resource utilization**: Health systems must anticipate demand for services. Utilization patterns vary dramatically across patient subgroups defined by combinations of clinical and demographic characteristics.

Traditional linear regression assumes that each predictor contributes additively to the outcome, with a constant effect across all patients. But in healthcare, this assumption often fails dramatically. For example, the effect of diabetes on healthcare costs might be minimal for young, otherwise healthy patients but substantial for elderly patients with multiple comorbidities. Tree-based models excel at capturing these kinds of complex interactions automatically, without requiring the analyst to specify them in advance.

## Why Trees? The Intuition Behind Recursive Partitioning

The fundamental idea behind tree-based prediction is elegantly simple: **divide patients into groups with similar outcomes, then predict the average outcome for each group**. This process of recursive partitioning creates a hierarchical structure that resembles an inverted tree, with the root at the top containing all patients and branches leading down to "leaves" (terminal nodes) containing homogeneous subgroups.

Consider predicting annual healthcare costs. A tree algorithm might first split patients into those with prior-year costs above versus below $10,000. Among high-cost patients, it might further split by age (over 65 vs. under 65). Among low-cost patients, it might split by presence of chronic conditions. This continues until we have groups that are relatively homogeneous in their healthcare costs.

The beauty of this approach is that:

1. **Interactions are automatic**: If diabetes only matters for elderly patients, the tree will naturally split by age first, then by diabetes only in the elderly branch.

2. **Non-linearities are handled**: The tree doesn't assume that the effect of age is linear—it can create different predictions for ages 20-40, 40-60, and 60-80 if that's what the data support.

3. **Results are interpretable**: A tree can be visualized and explained to non-technical stakeholders. "Patients over 65 with prior hospitalization and diabetes are predicted to cost $45,000" is much more accessible than a regression equation.

4. **No variable scaling needed**: Unlike penalized regression, trees are invariant to monotonic transformations of predictors—you don't need to worry about standardization.

## Connection to Last Week: The Prediction Framework

Last week, we learned about penalized regression methods (Ridge, LASSO, Elastic Net) for prediction. This week, we explore an entirely different approach to the same fundamental problem: predicting outcomes from patient characteristics while avoiding overfitting.

Both approaches share common principles:

- **Training vs. test data**: We evaluate predictive performance on data not used to build the model
- **Cross-validation**: We use CV to select tuning parameters that balance bias and variance
- **Regularization**: We control model complexity to prevent overfitting

However, the methods differ fundamentally in how they model the relationship between predictors and outcome:

| Aspect | Penalized Regression | Tree-Based Models |
|--------|---------------------|-------------------|
| Functional form | Linear combinations | Piecewise constant |
| Interactions | Must be specified | Automatic |
| Interpretability | Coefficients | Visual tree structure |
| Feature selection | Via shrinkage (LASSO) | Via split selection |
| Prediction surface | Smooth | Step function |

By the end of this module, you'll understand when each approach is most appropriate and how to compare their performance for healthcare prediction problems.

# Conceptual Foundations

## How Trees Make Predictions: The Big Picture

Before diving into the algorithmic details, let's understand the conceptual framework. A regression tree predicts a continuous outcome (like healthcare costs) by:

1. **Partitioning** the predictor space into rectangular regions
2. **Assigning** a predicted value to each region (the average outcome of training observations in that region)

For a new patient, we simply determine which region their predictor values fall into and predict the corresponding average. This is fundamentally different from regression, which computes a weighted sum of predictor values.

### Visual Intuition

Imagine predicting healthcare costs based on just two variables: age and number of chronic conditions. A regression tree might create predictions like this:

- **Region 1**: Age < 50 AND Conditions < 2 → Predict $3,000
- **Region 2**: Age < 50 AND Conditions ≥ 2 → Predict $8,500
- **Region 3**: Age ≥ 50 AND Conditions < 3 → Predict $12,000
- **Region 4**: Age ≥ 50 AND Conditions ≥ 3 → Predict $35,000

Notice how the tree captures an interaction: for younger patients, having 2+ conditions increases predicted costs from $3,000 to $8,500 (a 2.8x increase). For older patients, going from <3 to ≥3 conditions increases predicted costs from $12,000 to $35,000 (a 2.9x increase). The tree automatically discovered that the "cost impact" of chronic conditions varies by age group.

## The Recursive Partitioning Algorithm

Now let's understand how the algorithm constructs these partitions. The process is called "recursive binary splitting" because at each step, we:

1. Consider all possible ways to split the current region into two parts
2. Choose the split that most improves our predictions
3. Recursively apply the same process to each resulting region

### Step 1: Finding the Best Split

At each node, we need to decide:
- **Which variable** to split on
- **What value** to use as the cutoff

For a regression tree predicting a continuous outcome Y, the algorithm evaluates every possible split by computing the **reduction in sum of squared errors (SSE)**.

Suppose we're considering splitting predictor X at value c, creating two groups:

- **Left group (R₁)**: Observations where X < c
- **Right group (R₂)**: Observations where X ≥ c

For each group, the predicted value is simply the mean of Y for observations in that group:

$$\hat{y}_{R_1} = \frac{1}{n_1} \sum_{i: x_i < c} y_i \quad \text{and} \quad \hat{y}_{R_2} = \frac{1}{n_2} \sum_{i: x_i \geq c} y_i$$

The SSE for this split is:

$$\text{SSE}(X, c) = \sum_{i: x_i < c} (y_i - \hat{y}_{R_1})^2 + \sum_{i: x_i \geq c} (y_i - \hat{y}_{R_2})^2$$

The algorithm tries every variable and every possible cutoff value, selecting the combination (X*, c*) that minimizes SSE. This is a "greedy" approach—we make the locally optimal choice at each step without considering whether a different choice might lead to a better tree overall.

### Step 2: Recursive Splitting

Once we've made the first split, we have two regions. We now apply the exact same process to each region independently:

1. Among observations in the left region, find the best split
2. Among observations in the right region, find the best split
3. Continue recursively on each resulting region

This process creates a tree structure where each internal node represents a split decision and each terminal node (leaf) represents a prediction.

### Step 3: Stopping Criteria

The algorithm must know when to stop splitting. Common stopping criteria include:

- **Minimum node size**: Don't split nodes with fewer than some threshold of observations (e.g., 20)
- **Maximum depth**: Limit the number of levels in the tree
- **Minimum improvement**: Stop if no split improves SSE by more than a threshold

However, these early stopping rules are often too aggressive—they might prevent a "good" split that would occur later. Instead, modern implementations typically grow a large tree and then **prune** it back.

## Overfitting and the Need for Pruning

### The Problem: Trees Can Perfectly Fit Training Data

If we let a tree grow without restriction, it will continue splitting until each terminal node contains very few observations (perhaps even just one). Such a tree will have:

- **Zero training error**: Each prediction equals the actual outcome
- **Poor test performance**: The tree has memorized the training data, including its random noise

This is overfitting in its purest form. The tree is too complex—it has high variance (predictions change dramatically with different training samples) even though it has low bias (it can approximate any pattern).

### Visual Illustration of Overfitting

Consider predicting healthcare costs from age alone. Imagine we have 100 patients:

- A 1-split tree might divide patients into age < 50 vs. ≥ 50, giving 2 predictions
- A 10-split tree creates 11 predictions, each based on roughly 9 patients
- A 99-split tree creates 100 predictions, each based on 1 patient

The 99-split tree fits the training data perfectly but will perform terribly on new data because each prediction is based on a single patient's random cost variation.

### The Solution: Cost-Complexity Pruning

Rather than deciding when to stop growing, we grow a large tree and then prune branches that don't improve test performance enough to justify their complexity. This is done by minimizing a penalized error criterion:

$$\text{Cost-Complexity} = \text{SSE} + \alpha \cdot |T|$$

Where:
- **SSE** is the sum of squared errors on the training data
- **|T|** is the number of terminal nodes in the tree
- **α** (alpha) is a complexity parameter that controls the tradeoff

This should look familiar from last week! Just as LASSO penalizes regression coefficients to achieve a simpler model, cost-complexity pruning penalizes tree size. The parameter α plays the same role as λ in penalized regression:

- **α = 0**: No penalty → full tree (overfitting)
- **α large**: Heavy penalty → small tree (underfitting)

We use cross-validation to find the optimal α that minimizes prediction error.

### The 1-SE Rule

When selecting α via cross-validation, we often use the "one standard error rule":

1. Compute the cross-validated error for each value of α
2. Find α* that minimizes CV error
3. Select the largest α (simplest tree) whose CV error is within one standard error of the minimum

This rule trades a tiny bit of predictive accuracy for a substantially simpler, more interpretable tree. In practice, the simpler tree often performs just as well on truly new data.

## Advantages and Limitations of Trees

### Advantages

1. **Interpretability**: Trees can be visualized and explained to non-technical stakeholders. You can literally trace the path from root to leaf and understand why a prediction was made.

2. **No preprocessing required**: Trees handle numeric and categorical predictors naturally, don't require scaling/standardization, and are invariant to monotonic transformations.

3. **Automatic interaction detection**: If diabetes only matters for elderly patients, the tree will discover this automatically.

4. **Handle missing data**: Trees can use "surrogate splits" to make predictions when some values are missing.

5. **Computationally efficient**: Predictions are extremely fast—just a series of if-then comparisons.

### Limitations

1. **High variance**: Small changes in the training data can lead to very different trees. This instability is the primary motivation for ensemble methods.

2. **Piecewise constant predictions**: Trees approximate smooth relationships with step functions, which can be inefficient when the true relationship is smooth.

3. **Greedy algorithm**: The recursive splitting may miss globally optimal solutions because it doesn't look ahead.

4. **Extrapolation issues**: Trees cannot extrapolate beyond the range of training data—they simply predict the average of the nearest terminal node.

5. **Not ideal for additive relationships**: If the true model is Y = β₁X₁ + β₂X₂ (purely additive), a tree needs many splits to approximate this, while linear regression captures it exactly.

## Comparison with Regression Models

Let's compare how regression trees differ from the methods you've already learned:

### vs. Linear Regression

| Feature | Linear Regression | Regression Trees |
|---------|------------------|------------------|
| Functional form | Y = β₀ + β₁X₁ + ... | Piecewise constant |
| Assumptions | Linearity, normality | None on functional form |
| Interactions | Must specify | Automatic |
| Extrapolation | Extrapolates linearly | Cannot extrapolate |
| Interpretability | Coefficients | Visual tree |
| Training speed | Fast (closed form) | Moderate |
| Prediction speed | Fast | Very fast |

### vs. Penalized Regression (LASSO, Ridge)

| Feature | Penalized Regression | Regression Trees |
|---------|---------------------|------------------|
| Variable selection | Via shrinkage | Via split selection |
| Regularization param | λ (penalty weight) | α (pruning cost) |
| Prediction surface | Smooth | Discontinuous |
| Handling of many predictors | Excellent | Good |
| Feature importance | Coefficient magnitudes | Split-based importance |
| Ensemble extension | None (use as-is) | Random forests, boosting |

The key insight is that these methods are complementary. In practice, you should try multiple approaches and compare their performance on held-out data.

```{r}
    base_cost = 1000 + 50 * age + 0.5 * age^2,

    # Condition costs (with interactions!)
    condition_cost = 3000 * diabetes + 2500 * hypertension +
                     5000 * heart_disease +
                     # Interaction: conditions cost more for older patients
                     50 * age * n_conditions,

    # Utilization-driven costs
    utilization_cost = 2000 * prior_er_visits +
                       15000 * prior_hospitalizations,

    # Behavior costs
    behavior_cost = 1500 * smoker + 50 * pmax(bmi - 30, 0),

    # Insurance effects (uninsured have lower recorded costs due to less care)
    insurance_effect = case_when(
      insurance == "Private" ~ 1.0,
      insurance == "Medicare" ~ 1.1,  # Higher utilization
      insurance == "Medicaid" ~ 0.9,
      insurance == "Uninsured" ~ 0.6
    ),

    # Combine all components
    expected_cost = (base_cost + condition_cost + utilization_cost +
                     behavior_cost) * insurance_effect,

    # Add realistic noise (log-normal to create heavy tail)
    annual_cost = round(expected_cost * exp(rnorm(n, 0, 0.3)))
  ) %>%
  # Clean up intermediate variables
  select(-base_cost, -condition_cost, -utilization_cost,
         -behavior_cost, -insurance_effect, -expected_cost)

# Convert categorical variables to factors
healthcare_data <- healthcare_data %>%
  mutate(
    sex = factor(sex),
    insurance = factor(insurance),
    region = factor(region),
    smoker = factor(smoker, labels = c("No", "Yes")),
    diabetes = factor(diabetes, labels = c("No", "Yes")),
    hypertension = factor(hypertension, labels = c("No", "Yes")),
    heart_disease = factor(heart_disease, labels = c("No", "Yes"))
  )

# Display dataset structure
cat("Dataset Overview:\n")
cat("================\n")
cat("Number of patients:", nrow(healthcare_data), "\n")
cat("Number of variables:", ncol(healthcare_data), "\n\n")

cat("Variables:\n")
str(healthcare_data, give.attr = FALSE)
```

### The Complexity Parameter (cp)

The complexity parameter `cp` is the most important tuning parameter. It controls the cost-complexity pruning discussed earlier:

- A split is only performed if it improves the model by at least `cp * (SSE of root node)`
- Higher `cp` → fewer splits → simpler trees
- Lower `cp` → more splits → complex trees

Let's see how `cp` affects tree size:

```{r}

#| fig-height: 10

    annual_cost ~ age + sex + bmi + smoker + diabetes +
                  hypertension + heart_disease + insurance +
                  prior_er_visits + prior_hospitalizations + region,
    data = healthcare_data,
```

**Observation:** As `cp` decreases, the tree grows larger with more terminal nodes. The challenge is finding the right balance—enough complexity to capture true patterns but not so much that we overfit.

# Extension to Random Forests

## The Problem with Single Trees

While regression trees are interpretable and capture complex relationships, they suffer from a critical problem: **high variance**. This means that small changes in the training data can lead to very different trees, making predictions unstable.

### Demonstrating Tree Instability

Let's see this instability in action by fitting trees to different bootstrap samples of our data:

```{r}
#| label: tree-instability
#| fig-height: 8

# Fit trees to 4 different bootstrap samples
par(mfrow = c(2, 2))

for (i in 1:4) {
  # Create bootstrap sample
  boot_idx <- sample(1:nrow(healthcare_data), replace = TRUE)
  boot_data <- healthcare_data[boot_idx, ]

  # Fit tree
  boot_tree <- rpart(
    annual_cost ~ age + sex + bmi + smoker + diabetes +
                  hypertension + heart_disease + insurance +
                  prior_er_visits + prior_hospitalizations,
    data = boot_data,
    method = "anova",
    control = rpart.control(cp = 0.02)
  )

  # Plot
  rpart.plot(boot_tree, main = paste("Bootstrap Sample", i), cex = 0.6)
}

par(mfrow = c(1, 1))
```

**Observation:** Notice how different the trees are! The same variables appear in different positions, different cutoff values are used, and different variables are selected. This instability is problematic because we don't know which tree structure is "correct."

## The Random Forest Solution

Random forests address tree instability through two key ideas:

### 1. Bagging (Bootstrap Aggregating)

Instead of building one tree, we build many trees on different bootstrap samples and average their predictions:

1. Draw B bootstrap samples from the training data
2. Fit a tree to each sample
3. For prediction, average across all B trees

This reduces variance because the averaging smooths out the individual trees' errors. If each tree has variance σ², and the trees are independent, the ensemble has variance σ²/B.

### 2. Random Feature Selection

Bagging alone isn't enough—the trees are too correlated because they all use the same best predictors at the top. Random forests add another layer of randomness:

- At each split, only consider a random subset of m predictors (not all p)
- This decorrelates the trees, making the averaging more effective
- Default: m = p/3 for regression, m = √p for classification

## Implementing Random Forests

Let's build a random forest for our healthcare cost prediction:

```{r}

  data = train_data,

  mtry = 4,           # Number of variables tried at each split
```

### Interpreting Variable Importance

**%IncMSE (Permutation Importance):**

For each tree, we predict the OOB samples and record the MSE. Then we randomly shuffle one variable and predict again. The increase in MSE reflects how important that variable is. Variables that cause large increases when shuffled are important.

**IncNodePurity (Impurity Importance):**

Sum of the reduction in squared error whenever the variable is used for a split, averaged over all trees.

**Healthcare Interpretation:**

The variable importance plot tells us which patient characteristics are most predictive of healthcare costs. For healthcare managers, this information can guide:

- Risk stratification programs
- Care management targeting
- Quality improvement initiatives

### Question 1: Algorithm Understanding

**A regression tree is being built to predict hospital length of stay. The algorithm is considering splitting patients by age at cutoff 65. There are 200 patients younger than 65 with mean LOS = 3.2 days, and 100 patients 65+ with mean LOS = 5.8 days.**

a) What would be the prediction for a 70-year-old patient after this split?
b) If the overall mean LOS before the split is 4.07 days, calculate the reduction in SSE from this split.
c) Why is finding the optimal split computationally intensive with continuous predictors?

::: {.callout-tip collapse="true"}
## Click for Answers

a) **5.8 days** - The prediction for any patient in a terminal node is the mean outcome of training observations in that node. A 70-year-old falls in the 65+ node with mean LOS = 5.8.

b) **Reduction in SSE:**

Before split: SSE = Σ(yᵢ - 4.07)² for all 300 patients

After split: SSE = Σ(yᵢ - 3.2)² for 200 young + Σ(yᵢ - 5.8)² for 100 old

The reduction = SSE_before - SSE_after

While we can't compute exact values without individual data, the intuition is that predictions are now closer to actual values because we've separated two groups with different means.

c) For a continuous predictor with n unique values, there are (n-1) possible cutoff points to evaluate. For each cutoff, we must compute the SSE for both resulting groups. With many predictors and many observations, this requires checking thousands of potential splits at each node.

:::

### Question 2: Overfitting and Pruning

**Explain why a regression tree with 100 terminal nodes fit to 100 training observations would be useless for prediction, even though its training MSE is zero.**

::: {.callout-tip collapse="true"}
## Click for Answer

This tree has perfectly memorized the training data—each terminal node contains exactly one observation, so the prediction equals the actual value and training MSE is zero.

However, the predictions reflect individual patient variation, not true underlying patterns. When applied to new patients, the tree will:

1. Assign them to a terminal node based on the path they follow
2. Predict the single training observation's outcome in that node
3. This prediction is essentially random from the new patient's perspective

This is extreme overfitting. The model has high variance (predictions would change completely with different training data) and will perform poorly on test data. Pruning reduces the tree to capture genuine patterns rather than noise.

:::

### Question 4: Random Forest Mechanics

**In a random forest with 500 trees predicting healthcare costs from 12 variables:**

a) How many variables would typically be considered at each split?
b) Why does considering only a subset of variables at each split improve the ensemble?
c) What is out-of-bag (OOB) error and why is it useful?

::: {.callout-tip collapse="true"}
## Click for Answers

a) **m = 12/3 = 4 variables** per split (default for regression is p/3).

b) **Decorrelates the trees**: If all trees considered all variables, they would all split on the same strongest predictor at the root, making them very similar. By randomly restricting the variables considered, different trees emphasize different predictors, making the ensemble more diverse. When we average diverse predictions, errors cancel out better than when averaging similar predictions.

c) **OOB error**: Each bootstrap sample includes only about 63% of observations. The remaining 37% are "out-of-bag" for that tree. We can predict these using the tree and compare to actual values. Averaging across all trees gives an error estimate without needing a separate test set. It's useful because:
   - No need to set aside test data
   - More efficient use of training data
   - Unbiased estimate of test error

:::
